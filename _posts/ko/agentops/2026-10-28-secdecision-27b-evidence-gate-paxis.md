보안 에이전트가 수집한 로그에 의심스러운 명령이 보이지 않습니다. 여기서 “그 명령은 실행되지 않았다”고 답해도 될까요? 로그 수집이 5분간 끊겼을 수도 있고, 다른 호스트를 조회했을 수도 있습니다. 검색 결과가 질문과 관련 있다고 해서 결론까지 보장하지는 않습니다.

우리가 Thaki-SecDecision-27B V2를 만든 이유는 이 간격 때문입니다. 보안 문서를 더 많이 찾거나 그럴듯한 분석 문장을 생성하는 대신, **현재 확보한 근거만으로 특정 주장을 확정할 수 있는지**를 판단하는 모델입니다. 2026년 10월의 독립 TEST 4,002건에서 사전에 정한 G0~G7 게이트를 모두 통과했습니다. 아래에서는 무엇을 판단하는지, 왜 V1은 실패했는지, Paxis 에이전트에 붙인다면 어디에 놓아야 하는지 설명합니다.

**현재 상태:** 모델 학습과 독립 TEST 판정은 완료됐습니다. Hugging Face 공개 패키지는 별도 검증 중이며, Paxis 또는 Autonomous SOC 운영 환경에 SecDecision V2가 배포된 것은 아닙니다.

## 검색 결과가 아니라 결론의 근거를 평가한다

SecDecision의 입력은 질문 하나와 문서 목록만이 아닙니다. 검증할 주장(claim), 그 주장을 성립시키는 데 필요한 사실, 증거 ID가 붙은 로그·문서 집합입니다.

예를 들어 “호스트 A에서 14:12에 PowerShell이 실행됐다”는 주장을 생각해 봅시다.

| 근거 | SecDecision이 구별해야 하는 의미 |
|---|---|
| A 호스트의 해당 시각 프로세스 실행 로그 | 주장을 직접 지지할 수 있음 |
| 다른 호스트에서 실행된 PowerShell 로그 | 관련은 있지만 해당 주장에는 불충분 |
| PowerShell 악용을 설명하는 ATT&CK 문서 | 기술 설명이지 사건 발생의 증거는 아님 |
| 특정 시각의 로그에 PowerShell 기록이 없음 | 수집 완전성이 검증되지 않았다면 미발생의 증거가 아님 |
| 수집 범위·시간·완전성이 검증된 기록에서의 명시적 부재 | 조건이 충분할 때 반증 근거로 검토 가능 |

따라서 모델이 해야 할 일은 단순한 관련성 점수 계산이 아닙니다. 각 근거가 무엇을 지지하는지 평가하고, 필요한 조건들이 모였는지 판단해야 합니다.

출력의 핵심 상태는 **SUPPORTED, REFUTED, INSUFFICIENT, CONFLICTED** 네 가지입니다. 앞의 두 상태는 주장을 지지하거나 반박할 증거가 충분하다는 뜻이지, 보안 조치를 자동 승인한다는 뜻이 아닙니다. INSUFFICIENT는 증거가 부족한 상태이고, CONFLICTED는 서로 양립할 수 없는 근거를 해결하지 못한 상태입니다.

## V1에서는 분류 점수가 올랐지만 더 위험해졌다

첫 번째 실패는 모델 크기가 아니라 학습 목표에서 나왔습니다. V1에서는 증거 관계의 Macro-F1이 **0.6273에서 0.7310으로 개선**됐지만, 증거가 불충분한데도 결론을 허용하는 **False-ENOUGH는 1.79%에서 3.19%로 증가**했습니다. 보안 에이전트에 중요한 지표는 오히려 나빠진 것입니다.

라벨 정의에도 문제가 있었습니다. 같은 ATT&CK 계열의 다른 기술을 설명하는 문서를 실제 반증(CONFLICTING)처럼 다루면, 모델은 “비슷하지만 해당 사건의 증거는 아님”과 “해당 주장을 명시적으로 반박함”을 혼동하게 됩니다.

V2에서는 개별 근거의 관계를 판단하는 **Relation Head**와 증거 집합의 충분성을 판단하는 **Sufficiency Head**를 분리했습니다. 기반 모델은 Qwen3.8-27B이며, LoRA와 두 판단 헤드를 학습했습니다. 총 3,334 step, 약 8.8 GPU-hour를 사용했습니다.

그런데 학습 중 ENOUGH recall이 0.48 부근에서 정체됐습니다. 확인해 보니 모델이 지지 증거를 못 찾는 문제가 아니었습니다. 기존 판정 규칙이 “미충족 사실 0개”를 **지지와 반증 양쪽에 동일하게 요구**해, 올바른 반증 결론까지 차단하고 있었습니다. 당시 CALIB 분석에서 지지 방향 recall은 0.970인데 반증 방향 recall은 0.003이었습니다.

이를 수정한 **Rule B**는 지지 결론에는 필요한 사실 충족을 요구하되, 반증 결론에는 명시적 반증 또는 검증 가능한 완전 수집 근거를 요구합니다. 해결되지 않은 충돌은 계속 결론을 막습니다. 이 규칙 변경은 TEST 개봉 전에 amendment로 기록했고, 모델 가중치·체크포인트·임계값은 고정한 채 평가했습니다.

## TEST 4,002건에서 무엇을 확인했나

최종 모델은 **ckpt-02200 + Rule B + 고정 임계값**입니다. 모델과 평가 조건을 고정한 뒤 TEST 4,002건을 한 번 개봉했고, G0~G7 게이트가 전부 통과했습니다.

| 지표 | SecDecision V2 | 고정 zero-shot Stock |
|---|---:|---:|
| False-ENOUGH | **1/2,668 (0.04%)** | 202/2,668 (7.57%) |
| ENOUGH recall | **1,297/1,334 (97.23%)** | 390/1,334 (29.24%) |
| FULL recall | **94.60%** | 5.55% |
| REFUTE_COVERAGE recall | **99.85%** | 52.92% |
| ADJACENT False-ENOUGH | **0%** | 7.2% |
| Evidence relation Macro-F1 | **0.9634** | 동일 헤드 비교 없음 |
| Pairwise accuracy | **0.9975** | 동일 헤드 비교 없음 |

V2의 False-ENOUGH 1건은 PARTIAL 유형에서 나왔습니다. ADJACENT·ABSENT·CONFLICT 유형에서는 0건이었고, 입력에 없는 evidence ID를 출력한 사례도 0건이었습니다. 별도의 claim family·log format 분리 구간에서도 False-ENOUGH 0, ENOUGH recall 95.67%를 기록했습니다.

**이 표를 읽을 때 중요한 제한이 있습니다.** Stock은 4,002건 중 3,370건(83.96%)에서 파싱에 실패했습니다. 빈 출력이 나오거나 64-token 예산을 추론 텍스트에 사용해 JSON 결론까지 도달하지 못한 사례가 포함됩니다. 따라서 이 비교는 **고정된 zero-shot 평가 계약에서의 결과**입니다. 충분히 조정한 생성 예산·thinking 설정의 Stock보다 V2가 이만큼 우수하다고 주장할 수는 없습니다. 다만 V2 자체의 낮은 False-ENOUGH와 높은 recall, 사전 고정된 게이트 통과는 별도로 확인됐습니다.

또한 TEST는 운영 SOC 데이터와 같지 않습니다. 분리 평가 구간을 포함하지만, 실제 고객의 로그 누락·조직별 필드·악의적 증거 주입까지 검증했다는 의미는 아닙니다. 이 모델은 독립적인 침해 탐지기나 자동 차단 시스템이 아닙니다.

## Paxis에서는 판단 단계 한 곳에 둔다

Paxis에 이 모델을 적용한다면 기존 에이전트의 전체 LLM을 바꿀 필요가 없습니다. 에이전트가 정보를 모은 뒤, 답변을 확정하기 직전에 **근거 충분성 판단 단계**를 두는 방식이 자연스럽습니다.

~~~mermaid
flowchart TD
  A["Paxis 보안 분석 요청"] --> B["읽기 전용 검색·도구 호출<br/>로그·문서·코드 증거 수집"]
  B --> C["검증할 주장 + evidence ID 구성"]
  C --> D["SecDecision-27B V2<br/>근거 관계·충분성 판정"]
  D -->|"SUPPORTED / REFUTED"| E["근거를 인용한 분석 초안"]
  D -->|"INSUFFICIENT"| F["추가 조회 또는 검토 요청"]
  D -->|"CONFLICTED"| G["모순 표시·사람 검토"]
  E --> H["Paxis 정책·감사 기록"]
  F --> H
  G --> H
  H --> I["외부 변경·조치는 별도 승인"]
~~~

*위 흐름은 적용 구상입니다. SecDecision V2의 Paxis 실제 연동·운영 성능을 검증했다는 뜻은 아닙니다.*

코드 보안 검토에서도 역할을 나눌 수 있습니다. [SecProof](https://thakicloud.com/tech-blog/ko/agentops/secproof-2b-paxis-security-agent/)가 테넌트 격리·도구 승인 경계의 **취약 가능성과 코드 위치**를 판단한다면, SecDecision은 그 주장에 딸린 코드 증거·테스트 결과가 **확정을 허용하는지** 점검하는 보조 단계가 될 수 있습니다. 샌드박스 테스트와 정책 검사는 여전히 모델 외부에 남습니다.

예를 들어 SecProof가 “테넌트 격리 위반 가능성”을 제기했더라도, 실제 요청 경로를 확인할 코드와 재현 테스트가 없다면 Paxis는 이를 확정 취약점으로 처리해서는 안 됩니다. SecDecision의 INSUFFICIENT는 필요한 파일이나 테스트를 더 확인하라는 신호로 쓸 수 있습니다. 반대로 SUPPORTED가 나와도 곧바로 패치 반영이나 외부 조치를 실행하는 권한은 주지 않습니다.

일반 문서 RAG에도 같은 구분이 적용됩니다. 검색기와 [CiteRank](https://thakicloud.com/tech-blog/ko/agentops/citerank-4b-paxis/) 같은 모델은 **어떤 문서를 먼저 볼지** 돕고, SecDecision은 **그 문서들만으로 해당 주장을 말해도 되는지**를 판단합니다. 이 두 단계는 비슷해 보이지만 목적이 다릅니다.

## 공개 모델을 사용할 때 남겨야 할 경계

SecDecision V2의 추론 결과는 근거와 함께 기록해야 합니다. 원본 evidence ID, 주장, 모델·판정 규칙 버전, 임계값, 최종 상태를 남기면 왜 답을 보류했는지 나중에 재검토할 수 있습니다.

반증을 다룰 때는 특히 조심해야 합니다. 단순히 “로그에 없다”는 것을 “없었다”로 바꾸지 않고, 수집 범위와 완전성을 별도 근거로 확인해야 합니다. 모델의 점수는 운영에서 확률 보증서가 아니며, 이번 TEST에 사용한 임계값을 다른 고객 환경에 그대로 옮겨도 같은 위험 수준이 유지된다고 보장할 수 없습니다.

이번에 만든 것은 에이전트가 더 자신 있게 말하도록 하는 모델이 아닙니다. **증거가 모자랄 때는 말하지 않을 수 있도록 판단 지점을 분리한 모델**입니다. 실제 Paxis 통합은 아직 다음 단계로 남아 있습니다. 그 전에 모델 자체의 성능과 실패 조건부터 공개하는 것이 순서라고 생각했습니다.
