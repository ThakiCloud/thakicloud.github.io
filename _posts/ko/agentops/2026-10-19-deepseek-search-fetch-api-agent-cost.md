에이전트를 프로덕션에 돌리는 사람이라면, 이번 발표가 비용 테이블에 새 한 줄을 추가합니다. 결론부터 말하면, DeepSeek가 검색과 fetch를 독립 API로 내놓으면서 에이전트가 웹에 손을 뻗는 두 단계가 단품으로 분리됐고, 성공 1000회당 각 0.75달러를 붙였다는 점입니다.

![검색 노드가 문서 노드로 이어지며 에이전트 루프를 이루는 형상을 추상화한 이미지](/assets/images/deepseek-search-fetch-api-agent-cost-hero.webp)
*에이전트가 웹에 손을 뻗는 두 단계가 단품 비용으로 분리되는 개념을 형상화했습니다.*

## 왜 읽어야 하나

에이전트 루프의 비용을 모델 토큰 단 하나로만 계산하는 사람이라면, 이 글이 그 계산법을 바꿉니다. 에이전트가 웹에서 답을 끌어오는 과정은 보통 검색, fetch 두 단계로 나뉘는데, 그동안 이 두 단계는 각 검색 공급사의 API로 흩어져 있어 루프 단위 비용으로 모으기가 어려웠습니다. DeepSeek가 이 두 단계를 한 집합으로, 같은 단가 구조로 내놓은 것은 에이전트 비용의 분리가 더 선명해졌다는 뜻입니다. 2026년 11월 1일(베이징 시간 00:00)부터 청구됩니다.

## 개요

에이전트가 실시간 정보를 쓰려면 두 동작이 필요합니다. 검색으로 출처를 찾는 동작, fetch로 그 출처의 본문을 가져오는 동작입니다. 이 둘은 성격이 다릅니다. 검색은 쿼리를 받아 결과 목록을 반환하고, fetch는 URL을 받아 문서를 반환합니다. 그동안 검색 API는 Brave, Exa 같은 공급사가 따로 두고, fetch는 크롤링이나 별도 도구로 했습니다.

DeepSeek의 Search와 Fetch API는 이 두 동작을 한 집합으로 묶어, 요청 단위로 청구합니다. 두 API 모두 성공 요청 1000회당 0.75달러입니다. 실패한 요청은 돈을 받지 않습니다. 이 점이 에이전트 비용 계산에서 중요한데, 루프에서 빈 결과가 섞여도 그 비율만큼 청구가 깎인다는 뜻입니다.

## Search와 Fetch, 어떤 단가인가

DeepSeek 공식 API 문서에 따르면 Search와 Fetch는 독립 API로, 요청 단위로 청구됩니다. 두 API 모두 성공 요청 1,000회당 0.75달러입니다.

| 항목 | 값 |
|---|---|
| Search | 성공 1,000회당 $0.75 |
| Fetch | 성공 1,000회당 $0.75 |
| 청구 시작 | 2026-11-01 00:00 (베이징) |
| 청구 단위 | 성공 요청 |

검색과 fetch를 한 사이클에 함께 쓰면, 1,000회 기준으로 대략 $1.50이 됩니다. 일부 보도는 이 단가가 Brave와 Exa의 검색 API 가격보다 낮다고 전합니다. 공급사별 비교 수치는 DeepSeek 공식 발표에만 있지 않아 [추정]으로 다룹니다.

같은 시점에 DeepSeek는 모델 V4.1-Flash-1017도 내놓았다고 보도됩니다. 검색 API와 모델 업데이트가 같은 주에 나온 것은, 검색을 에이전트가 쓰는 모델 루프에 붙이는 쪽으로 방향이 맞춰졌다는 읽을 맛입니다.

## 루프 비용에 새 줄이 생겼습니다

에이전트 비용은 그동안 모델 호출 토큰 단가만 세었습니다. 검색과 fetch는 그 뒤에 붙는 부대 비용이었습니다. DeepSeek가 이 둘을 독립 단품으로 내놓으면서, 비용 테이블에서 모델 토큰 옆에 두 줄이 또 생겼습니다.

이 두 줄의 크기는 루프의 성격에 달립니다. 검색을 한 번만 하고 끝나는 질의응답이면 미미합니다. 매 단계에서 웹을 확인하는 에이전트, 여러 출처를 fetch해 교차 검증을 하는 에이전트는 이 두 줄이 커집니다. 성공만 청구라는 구조가 여기서 빛을 보입니다. 빈 결과가 섞인 루프는 실제 성공 비율만큼만 내면 됩니다.

에이전트 비용을 설계할 때, 이제 물어야 할 것이 하나 늘었습니다. 이 루프에서 검색과 fetch를 몇 번 호출하는가. 토큰 단가만 보고 에이전트를 짠다면, 웹 접지 비용이 어느 순간 모델 비용의 상당 부분이 될 수 있습니다.

## ThakiCloud 제품 적용 시사점

Paxis는 에이전트가 도구를 부르는 구조를 일급 시민으로 다룹니다. Search와 Fetch가 독립 단품이 된 것은, Paxis의 도구 호출 계층에서 이 두 호출이 비용 게이트를 통과할 대상이 됐다는 뜻입니다.

에이전트가 도구를 부를 때마다 Paxis는 정책 게이트와 감사 로그를 거칩니다. 검색과 fetch도 이 흐름에 들어옵니다. 성공 1,000회당 0.75달러라는 단가가 있으면, Paxis는 루프의 총 도구 비용을 예산에 맞출 수 있습니다. 어느 에이전트가 검색을 지나치게 부르는지, fetch 실패가 어느 공급사 URL에서 몰리는지를 비용 데이터로 볼 수 있습니다.

에이전트 루프의 총비용은 모델 토큰과 도구 호출입니다. 이 둘을 같은 장부에서 보면, 토큰만 줄여도 비용이 그대로인 루프를 잡을 수 있습니다. 웹을 자주 확인하는 루프는 토큰이 아껴도 검색·fetch로 나갑니다. Paxis의 관측 계층이 이 분리를 보여줄 때, 에이전트 단가가 비로소 전체가 됩니다.

## 한계 및 반론

Search와 Fetch의 성공 청구 구조는 유리해 보이지만, 검색 결과의 품질은 이 단가와 별개입니다. 값싼 검색이라도 결과가 낡으면 fetch로 가져와야 할 URL이 바뀌고, 결국 토큰이 더 쓰입니다. 단가만으로 공급사를 고르면 품질 문제가 뒤따릅니다.

1,000회당 0.75달러는 성공 기준이고, 빈 결과를 반환하는 횟수는 청구되지 않습니다. 하지만 빈 결과를 돌려주는 자체가 에이전트가 다시 검색하게 만든다면, 미청구 호출도 루프 시간과 모델 토큰을 씁니다. 청구가 없어도 비용은 생깁니다.

또한 이 API가 모든 지역에서 즉시, 어떤 용량 제한 없이 쓰인다는 공식 발표는 없습니다. 문서에는 모델별 동시 요청 한도가 적혀 있고, Search와 Fetch의 한도는 별도로 명시되지 않습니다. [추정]으로, 대규모 루프에서는 한도와 레이턴시가 단가보다 먼저 병목이 될 수 있습니다.

## 정리

DeepSeek가 Search와 Fetch를 독립 단품으로 내놓은 것은 검색이 비싸서가 아니라, 에이전트가 웹을 쓰는 두 단계가 비용으로 분리됐기 때문에 중요합니다. 1,000회당 각 0.75달러, 성공만 청구, 11월 1일 시작이라는 세 수치는 루프 비용 테이블에 새 두 줄을 씁니다. 이제 에이전트를 짤 때 물어야 할 것이 하나 늘었습니다. 이 루프는 검색과 fetch를 몇 번 부르는가. 모델 토큰만 세던 비용 계산은, 웹 접지가 단품이 된 순간부터 더 정확하지 않습니다. Paxis처럼 도구 호출을 일급 시민으로 다루는 플랫폼이 이 두 줄을 장부에 합칠 때, 에이전트의 진짜 단가가 보입니다.
